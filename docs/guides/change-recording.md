# 改动记录规则

## 目的与位置

根目录 `CHANGELOG.md` 是这个 fork 的定制改动索引，供本人、协作者和后续代理查看。
它记录与上游相比做了哪些定制、为什么做、影响什么，以及哪些效果已经确认。
它与代码一起保存在 Git 中并随提交推送到 fork。

## 必须遵守的流程

1. 开始修改前，阅读最近记录，确认当前已有能力和限制。
2. 每个有实际意义的改动分配一个稳定编号，从 `C0001` 递增，不重复、不重新编号。
   同一次修改中尚未提交的补充可以更新同一条记录；已经提交的后续修复另开编号，引用原记录。
3. 完成改动时同步填写原因、前后行为、文件和验证状态。记录以最终 diff 和实际结果为依据，不能只复述计划。
4. 提交前检查已修改文件和新增文件；每一项应能对应到记录。生成文件应注明来源。
5. 将相关代码和记录放进同一个提交。一项逻辑变化一个提交；需要多个提交时分别关联相应记录。
6. 提交标题遵循英文 Conventional Commits；正文加 `Change-Id: C0001`。一条提交涉及多个编号时逐行填写。
7. 推送前汇总本次编号、主要变化、验证结果和未解决问题。推送后核实实际目标仓库与分支，再报告完成。

记录覆盖代码、UI、配置、构建/签名方式、依赖、规范与说明文档的实际变更。
同一逻辑变化里的排版微调或生成文件不用单独编号；不能借此漏记独立功能或行为变化。

## 写法

- 面向未来的自己，用中文写清具体变化，例如“底部新增测试入口，原三个入口保留”。
- 文件路径使用仓库相对路径，可按同一作用分组；写清入口文件和关键实现文件。
- 日期使用北京时间 `YYYY-MM-DD`。同一天的多个改动由编号区分。
- 区分“已实现”“编译通过”“安装成功”“实际使用确认”和“尚未验证”。未执行的测试写明原因。
- 依赖某个 Host、系统版本、登录服务或签名配置的行为必须注明。
- 修复或撤销已有变化时引用原编号，保留旧记录，用后续记录说明现状。
- 不记录密码、会话令牌、私钥、设备敏感标识、一次性配对码、完整配对链接或用户聊天内容。
- 不把计划当作已完成改动；确有未完成工作，放在对应记录的“限制/待办”中。

## 模板

```markdown
### C0000 · YYYY-MM-DD · 改动标题

- 原因：具体需求或遇到的问题。
- 变化：修改前是什么，修改后是什么；说明会影响的原有能力。
- 文件：`path/to/file`，以及其他关键文件。
- 验证：实际执行的编译、安装或使用结果；未执行项及原因。
- 限制/待办：版本依赖、尚未确认的效果、后续事项；没有则写“无已知新增限制”。
- 关联：相关记录编号；首次独立变化写“无”。
```

提交编号的示例：

```text
feat(ios): add a fourth navigation tab

Change-Id: C0001
```

通过 `git log --all --grep='Change-Id: C0001'` 查找对应提交。
不要为了填写当前提交的哈希反复修改记录；尚未提交的改动也不得编造哈希或声称已推送。
